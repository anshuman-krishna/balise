# Architecture decision records

Numbered, append-only. An ADR records a decision that was hard to make and would
be expensive to revisit, along with the reasoning that was available at the
time.

## Rules

- **Never delete an ADR, and never rewrite one.** A decision that no longer
  holds gets a new ADR that supersedes it, and the old one is marked
  `Superseded by NNNN` in its status line. The wrong turning is part of the
  record: knowing what was considered and rejected is most of the value.
- **Numbers are permanent.** `0007` is `0007` forever, whatever happens to it.
- One decision per record. If a record has two decisions in it, it is two
  records.
- Write the consequences honestly, including the ones that cost something. A
  record listing only benefits is a press release.

## What needs one

The operating manual names four credibility areas: measurement, statistics, the
ledger, and the criteria engine. A change to any of them needs an ADR. Beyond
that:

- Any change to `classifyDelta`, without exception.
- Anything that changes what a historical report would say if it were
  regenerated.
- Anything in `docs/METHODOLOGY.md`, which additionally needs a version bump and
  a migration note.
- A change to the shape of a rule pack, or to how packs are versioned.
- A choice between architectures where the rejected option was reasonable.

Smaller decisions live in `PLAN.md`'s decisions log, which is a running record
rather than a considered one. An entry there graduates to an ADR when someone
would otherwise have to reconstruct the reasoning from a diff.
